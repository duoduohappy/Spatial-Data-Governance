# POI 数据交付验收试点

状态：尚未开始。已具备工程和记录模板，未取得真实交付材料及独立业务审核结果。

## 试点范围

首批建议选择 10-20 个实际交付批次，包含明确规则、缺失信息、冲突要求和按来源区分的更新时间要求。先用现有能力覆盖 CSV / 二维 Point GeoJSON、显式 EPSG:4326、一个简单 Polygon。按来源的多实例目前只支持 freshness，其他规则仍保留首版边界。

## 需要的材料

每批五个文件：delivery_spec.md、dictionary.csv、poi.csv（或 poi.geojson）、area.geojson、crs.json。字典必须声明字段、类型、必填与枚举。若按来源检查，source 需为显式字符串枚举。

支持的范围语法举例：`仅对 source="municipal" 的记录，数据距明确基准时间不得超过 7 天。` 每个来源单独成条款，阈值及基准时间必须在该条款有证据。不猜测别名、不补时间、不以其他来源代替。无匹配数据或来源无法识别时不能判通过。

真实原始文件保存在本机 work/pilot/ 等运行目录，不提交 GitHub；不要把 API Key、业务敏感说明或个人信息写进公开评测文件。当前协作仅使用本地模型，无自动云端外发。

## 人工金标准

1. 在看模型输出前，由业务审核人逐条标注原文、支持状态、必检/参考、规则类型、参数和适用范围，填写 eval/pilot-template/labels.csv 的副本。
2. 条件允许时由第二位业务人员独立标注，再对分歧仲裁。保留分歧记录，不以模型答案回填人工标签。
3. 确认后冻结文件 SHA-256、标签版本与评测标准；后续文档变化另开版本，已用于调参的数据标记为开发集。

## 对照与测量

对相同输入比较 single / self_review / dual_review，冻结模型、提示词、预算及工具权限；同角色自检与双角色同为最多四次调用，报告实际消耗。单次生成只有一次调用，不能说三组使用了相同实际 Token。

记录：完整规则映射、遗漏、缺失信息误判、来源错误、人工改动数、模型等待时间、端到端时间、人工有效审核时间和调用用量。人工时间应由实际审核过程计量，不用模型耗时或改动数替代。可交错分配批次顺序，避免同一人熟记答案造成偏差。

首次开发对照中双角色未胜过单次生成，因此默认仍为 single。不得仅因换成多 Agent 就宣称提效。是否采用，应由冻结标准和真实业务效果决定。

## 审批与整改

模型及审查 Agent 均不能批准。人审时核对所有条件、字段、范围和未解决要求；一次模型修订后仍需人工确认。来源字段变化会改变记录的适用范围，目前没有批准重分类通道，因此必须业务复核，不能用移出原规则范围来关闭问题。

报告应同时披露批次自身结论和整改台账状态；只有同规则、同实体、有完整正面执行证据才能关闭。

## 试点退出标准

实际业务方预先确认关键规则与误放行容忍度；保留明确的失败/未知反例。若协作没有稳定收益，保留单 Agent 与人工审核，不降低安全门槛来制造提升。完成业务签认后再更新项目成果和简历；当前仅完成工程升级，不属于客户生产上线或 ROI 证明。
